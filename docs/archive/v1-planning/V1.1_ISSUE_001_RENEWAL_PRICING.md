## Executive Summary

**Problem:** Snapshot prices in `BusinessSubscriptionFeature` are never updated at renewal time, causing customers to keep old prices indefinitely despite receiving notifications about price changes.

**Solution:** Implement automatic price update at renewal with audit trail.

```typescript
/**
 * apply-renewal-price-updates.ts
 *
 * Server function: Update BusinessSubscriptionFeature snapshot prices to match
 * the current active PricingCatalog at subscription renewal time.
 *
 * Called by:
 *   - Stripe webhook (handleSubscriptionUpdated) when period advances
 *   - Background job (optional future enhancement)
 *
 * Business Rule (per ADR-011):
 *   - Prices auto-update at renewal (customers receive 7-day warning)
 *   - All changes are logged to BusinessSubscriptionFeaturePriceHistory
 *   - Only COMPOSABLE_FEATURES subscriptions are affected
 *
 * Atomicity:
 *   - All updates happen in a single transaction
 *   - If catalog load fails or any update fails, entire operation rolls back
 */

import type { PrismaClient } from 'prisma/generated/prisma/client'
import { createPricingCatalogRepositoryWithDeps } from '../billing/pricing/pricing-catalog-repository'
import { PricingEngine } from '../billing/pricing/pricing-engine'
import type { BusinessSubscriptionFeatureDTO } from '../billing/pricing/types'
import type { CapabilityKey } from '../entitlement/capability-keys'

export type ApplyRenewalPriceUpdatesResult =
  | { success: true; updatedCount: number; unchangedCount: number }
  | { success: false; error: string }

/**
 * Update snapshot prices for a single subscription to match current catalog.
 */
export async function applyRenewalPriceUpdates(
  prisma: PrismaClient,
  subscriptionId: string,
): Promise<ApplyRenewalPriceUpdatesResult> {
  try {
    // 1. Load subscription and verify it's COMPOSABLE_FEATURES
    const subscription = await prisma.businessSubscription.findUnique({
      where: { id: subscriptionId },
      select: {
        id: true,
        billingModel: true,
        businessSubscriptionFeatures: {
          select: {
            featureKey: true,
            snapshotPrice: true,
            catalogVersion: true,
          },
        },
      },
    })

    if (!subscription) {
      return { success: false, error: `Subscription ${subscriptionId} not found` }
    }

    if (subscription.billingModel !== 'COMPOSABLE_FEATURES') {
      // Not applicable to predefined plans — skip silently
      return { success: true, updatedCount: 0, unchangedCount: 0 }
    }

    if (subscription.businessSubscriptionFeatures.length === 0) {
      return { success: true, updatedCount: 0, unchangedCount: 0 }
    }

    // 2. Load active pricing catalog
    const repo = createPricingCatalogRepositoryWithDeps(prisma)
    const activeCatalog = await repo.loadActive()

    if (!activeCatalog) {
      return { success: false, error: 'No active PricingCatalog found' }
    }

    // 3. Build snapshots DTO for PricingEngine
    const snapshots: BusinessSubscriptionFeatureDTO[] = subscription.businessSubscriptionFeatures.map(f => ({
      subscriptionId: subscription.id,
      featureKey: f.featureKey as CapabilityKey,
      snapshotPrice: f.snapshotPrice,
      catalogVersion: f.catalogVersion,
    }))

    // 4. Detect price changes using existing PricingEngine logic
    const priceChanges = PricingEngine.validateGrandfatheredPrices(snapshots, activeCatalog)

    if (priceChanges.length === 0) {
      // No price changes — nothing to update
      return { success: true, updatedCount: 0, unchangedCount: snapshots.length }
    }

    // 5. Apply updates atomically
    const now = new Date()

    await prisma.$transaction(async tx => {
      for (const change of priceChanges) {
        // Update snapshot price
        await tx.businessSubscriptionFeature.update({
          where: {
            subscriptionId_featureKey: {
              subscriptionId: subscription.id,
              featureKey: change.featureKey,
            },
          },
          data: {
            snapshotPrice: change.currentCatalogPrice,
            catalogVersion: activeCatalog.version,
            updatedAt: now,
          },
        })

        // Log to history
        await tx.businessSubscriptionFeaturePriceHistory.create({
          data: {
            subscriptionId: subscription.id,
            featureKey: change.featureKey,
            oldPrice: change.grandfatheredPrice,
            newPrice: change.currentCatalogPrice,
            oldCatalogVersion: change.snapshotCatalogVersion,
            newCatalogVersion: activeCatalog.version,
            changeReason: 'RENEWAL',
            appliedAt: now,
            appliedBy: null, // Automatic
          },
        })
      }
    })

    return {
      success: true,
      updatedCount: priceChanges.length,
      unchangedCount: snapshots.length - priceChanges.length,
    }
  } catch (err) {
    const msg = err instanceof Error ? err.message : String(err)
    return { success: false, error: `applyRenewalPriceUpdates failed: ${msg}` }
  }
}
```

- All imports should resolve
- No business logic changes needed (uses existing PricingEngine)

---

```markdown
## ADR-011 — Automatic Price Updates at Subscription Renewal

**Date:** August 18, 2026
**Status:** Accepted — Active
**Introduced in:** V1.1
**Related to:** ADR-009 (Composable Pricing Snapshot Model)
**Files:** `src/lib/server-fn/apply-renewal-price-updates.ts`

---

### Decision

Subscription renewal automatically updates `BusinessSubscriptionFeature` snapshot prices to match the current active `PricingCatalog`. Customers receive a 7-day advance notification (via `composable-renewal-preview` job) before the change takes effect.

---

### Problem Being Solved

ADR-009 introduced the snapshot model to prevent silent price changes — prices are frozen at subscription creation time. However, it did not specify what happens at renewal when catalog prices have changed.

Without renewal price updates, customers would remain on their original prices indefinitely, defeating the purpose of the catalog versioning system. The notification job warns customers but never actually applies the new prices.

---

### Alternatives Considered

**Option A: Automatic Update (CHOSEN)**
- Prices auto-update at renewal
- 7-day notification provides advance warning
- Standard SaaS behavior, minimal complexity

**Option B: Explicit Acceptance Flow**
- Customer must accept new prices before renewal
- Adds UI complexity, requires rejection handling
- Better customer control but significant implementation cost

**Option C: Grace Period (Hybrid)**
- Auto-update but allow 30-day revert window
- Most complex, requires additional state tracking

---

### Why Automatic Is the Right Choice

1. **User expectation alignment:** Customers receive clear notification 7 days before renewal stating the new price. This is standard SaaS practice.
2. **Minimal complexity:** Leverages existing `PricingEngine.validateGrandfatheredPrices()` logic.
3. **Audit trail:** All changes are logged to `BusinessSubscriptionFeaturePriceHistory`.
4. **Non-disruptive:** Customers can cancel or modify their subscription during the 7-day window if they disagree with the new price.

---

### Implementation Details

- **Trigger:** Stripe webhook `customer.subscription.updated` detects period advancement
- **Logic:** `applyRenewalPriceUpdates()` loads active catalog and updates snapshots
- **Atomicity:** All updates happen in a single transaction
- **Failure handling:** Errors are logged but don't fail the webhook (subscription status update takes priority)
- **History:** Every price change is logged with old/new prices and catalog versions

---

### Consequences

- Customers no longer stay on outdated prices indefinitely
- Price history table provides full audit trail for support inquiries
- Webhook processing time increases slightly (catalog load + updates)
- Renewal notifications now accurately reflect what will happen (not just "may happen")

---

### Future Enhancements

If customer feedback indicates need for explicit acceptance:
- Add `/billing/renewal-review` route showing pending price changes
- Allow feature selection adjustment before renewal
- Implement "lock price for N months" enterprise contract feature

---
```
